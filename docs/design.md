# Design

How the Wallet Service is built and how it meets the [requirements](requirements.md). This document grows with each increment.

## Architecture

The service follows a hexagonal (ports and adapters) layout inside a single Maven module, under the base package `com.ebravo.wallet`:

| Package | Responsibility | May depend on |
|---|---|---|
| `domain` | Wallets, ledger, money and the business rules around them | The JDK only |
| `application` | Use cases that orchestrate the domain through ports | `domain` and the JDK only |
| `adapter` | HTTP, persistence, security and other technology | `application`, `domain` |

Dependencies point inward: technology depends on the domain, never the other way around. Adapters do not depend on each other. The rules are enforced by `ArchitectureTest`, so a violation fails the build instead of waiting for code review.

## Technology

- Java 25, Spring Boot 4.1.
- PostgreSQL 18, Spring Data JPA (Hibernate), Flyway.
- Spring Security as an OAuth2 resource server (JWT).
- Maven through the Maven Wrapper.
- JUnit, AssertJ, ArchUnit, JaCoCo, PIT (mutation testing), Testcontainers.
- Docker Compose for local runs: the service image, built from source by a multi-stage Dockerfile, next to PostgreSQL and [mock-oauth2-server](https://github.com/navikt/mock-oauth2-server) as the local token issuer.
- An OpenAPI 3.1 contract, written by hand in `src/main/resources/openapi.yaml` and served at `GET /openapi.yaml`; Atlassian's openapi-request-validator checks the tests' exchanges against it.
- Micrometer metrics in Prometheus format, on a management port of its own.
- Structured logs in Elastic Common Schema, Spring Boot's own format, one JSON object per line.
- A [Bruno](https://www.usebruno.com) collection of every endpoint, in `bruno/`: usage examples and end-to-end checks.
- GitHub Actions, on every pull request and every push to `main`: `./mvnw verify`, and the Bruno collection against the stack Docker Compose starts.

## API

The contract is [`openapi.yaml`](../src/main/resources/openapi.yaml), served by the service at `GET /openapi.yaml`; this section summarizes it. Every endpoint except the probes and the contract requires a bearer JWT from the configured issuer, issued to the `wallet-service` audience. The wallet is always the caller's own, identified by the token subject.

| Method and path | Success | Errors |
|---|---|---|
| `POST /wallets` | `201`, `Location: /wallets/me`, `{id, currency, createdAt}` | `401`; `409` when the user already has a wallet; `503` past the three-second budget, database unavailable or the token cannot be checked |
| `GET /wallets/me` | `200 {id, currency, createdAt}` | `401`; `404` when the user has no wallet; `503` database unavailable or the token cannot be checked |
| `GET /wallets/me/balance`, optionally `?at=2026-11-09T10:00:00Z` | `200 {"balance": "0.00", "currency": "BRL"}`; with `at`, the balance at that instant | `400` `at` malformed or without offset; `401`; `404` when the user has no wallet; `422` `at` before the wallet was opened or in the future; `503` database unavailable or the token cannot be checked |
| `POST /wallets/me/deposits` `{"amount": "10.50"}`, header `Idempotency-Key` | `201`, `Location: /wallets/me/transactions/{id}`, the transaction; the same response again for a key already used with the same amount | `400` malformed request, `Idempotency-Key` missing or malformed; `401`; `404` no wallet; `422` amount not positive, more than 2 decimals or beyond the storable bound, a balance that would exceed it, or a key already used for another request; `503` wallet busy, past the three-second budget, database unavailable or the token cannot be checked |
| `POST /wallets/me/withdrawals` `{"amount": "10.50"}`, header `Idempotency-Key` | `201`, `Location: /wallets/me/transactions/{id}`, the transaction; the same response again for a key already used with the same amount | as deposits; `422` also when the balance is not enough |
| `POST /wallets/me/transfers` `{"recipientWalletId": "…", "amount": "10.50"}`, header `Idempotency-Key` | `201`, `Location: /wallets/me/transactions/{id}`, the transfer as the sender sees it; the same response again for a key already used with the same recipient and amount | `400` malformed request, `recipientWalletId` missing or not a full UUID, `Idempotency-Key` missing or malformed; `401`; `404` the caller has no wallet; `422` amount rules as deposits, balance not enough, recipient is the caller's own wallet, recipient wallet does not exist, its balance would exceed the storable bound, or a key already used for another request; `503` either wallet busy, past the three-second budget, database unavailable or the token cannot be checked |
| `GET /wallets/me/transactions?page=0&size=20` | `200 {"transactions": […], "page", "size", "totalElements", "totalPages", "next"}`, newest first | `400` `page` or `size` not a whole number in range; `401`; `404` no wallet; `503` database unavailable or the token cannot be checked |
| `GET /wallets/me/transactions/{id}` | `200`, the transaction | `400` id not a UUID; `401`; `404` no wallet, or no such transaction on the caller's wallet; `503` database unavailable or the token cannot be checked |
| `GET /livez`, `/readyz` | `200`, public | `401` when a token is sent and is not valid; `503` when down, `/readyz` also while the database is unavailable, and both when a token is sent and cannot be checked |
| `GET /openapi.yaml` | `200`, public, `application/yaml`, the whole contract (no ranges) | `401` when a token is sent and is not valid; `503` when a token is sent and cannot be checked |

A transaction is shown as the caller's wallet sees it: `{"id", "type": "DEPOSIT" | "WITHDRAWAL" | "TRANSFER", "amount": "-10.50", "balance": "0.00", "currency": "BRL", "counterpartyWalletId", "correlationId", "createdAt"}`. The amount is signed (negative when money left the wallet) and `balance` is the wallet's balance right after it. `counterpartyWalletId` is the other wallet of a transfer and is left out of deposits and withdrawals. Both wallets of a transfer read it at the same address, each with its own amount and balance.

The history lists the caller's transactions newest first, in the order they were posted, each as `GET /wallets/me/transactions/{id}` shows it (A20). `page` starts at 0 and defaults to 0; `size` defaults to 20 and goes from 1 to 100. `totalElements` counts every transaction of the wallet, `totalPages` the pages of that size, and `next` is the path of the next page, left out on the last one and past it. A page past the end is `200` with no transactions.

With `at`, the balance is the wallet's balance right after the last transaction posted at or before that instant, and `0.00` from the instant the wallet was opened until its first transaction (A6). `at` is ISO-8601 with an offset (A21); a positive offset is sent encoded (`%2B`), since a raw `+` in a query string is read as a space. Without `at`, the current balance is answered.

Amounts are decimal strings; a JSON number is refused. A request is `400` when it is not well-formed (invalid JSON, `amount` missing or not a plain decimal string), and `422` when it is well-formed but breaks a rule. A posting whose body is not sent as `application/json` is `415`.

Deposits, withdrawals and transfers require an `Idempotency-Key` of 1 to 64 letters, digits, `.`, `_`, `:` or `-` (A17). Sent again with a key the wallet already used, the operation answers with the transaction already posted, exactly as the first time (`201`, same `Location` and body, so the body keeps the original correlation id), and posts nothing (A18). Sent with another request (another operation, another amount, or for a transfer another recipient), it is refused with `422` and posts nothing; amounts are compared as money, so `"10.5"` and `"10.50"` are the same request (A19). The key belongs to the caller's wallet, across operations (A16); on a transfer, to the sender's.

Every response carries `X-Correlation-Id`: the caller's, if it sent a valid one, or a generated UUID. A malformed one is refused with `400`, on every path.

`503` comes with `Retry-After: 1`, for a wallet too busy to lock, a posting or wallet opening that ran past its three-second budget (D53), a database that is unavailable, or a token that cannot be checked because the issuer's keys cannot be read (D52). A busy wallet posted nothing, a posting past its budget was rolled back, and a token that cannot be checked reached nothing. A database failure is answered the same whether the database is down or the pool is full, and without telling at which step it came, so a posting is retried with the same `Idempotency-Key`: it replays if it was posted and posts once if it was not.

Every error the service decides is Problem Details (`application/problem+json`), a refused token too: its body is fixed, and the `WWW-Authenticate` challenge names what was wrong with it. A failure of the service itself still answers `500` with Spring Boot's generic error body (see trade-offs); `type` is left out when it is `about:blank`, as RFC 9457 allows. Timestamps are ISO-8601 in UTC. The contract does not list per operation the refusals HTTP itself defines (`405`, `406`), nor `500`.

## Decisions

| ID | Decision | Rationale |
|---|---|---|
| D1 | One wallet per user, single currency (BRL) | Multi-currency adds conversion and per-currency balances without serving any stated requirement. |
| D2 | Double-entry ledger with a system external account | Deposits debit the external account and withdrawals credit it, so every transaction balances to zero. Money can't appear or disappear without a record, which is the strongest audit guarantee. |
| D3 | Pessimistic locking | Under contention on the same wallet it is simpler and more predictable than optimistic locking with retries. |
| D4 | Mandatory idempotency keys | Clients of a mission-critical service retry on timeouts; without idempotency a retry can move money twice. |
| D5 | PostgreSQL, run through Docker | Row-level locking and concurrent writers are required by D3 and NFR4. Embedded databases such as SQLite lock the whole database on writes and can't be shared by multiple instances. |
| D6 | Paginated transaction listing | Low cost, and it makes the audit trail visible through the API. |
| D7 | JWT validated in the service, TLS at the infrastructure | Stateless token validation scales with the service. Token issuance belongs to an identity provider; a mock issuer covers local runs. In-process TLS would require self-signed certificates and hurt the out-of-the-box experience. |
| D8 | UTC storage, ISO-8601 with offset at the API | Ledger timestamps must be unambiguous; time zones are a presentation concern, and this API has no presentation layer. |
| D9 | Single Maven module, layering enforced by ArchUnit | Keeps the build simple. Multi-module would enforce the same boundaries at compile time, at the cost of more build configuration for a service of this size. |
| D10 | 100% line and branch coverage of the domain and application layers, enforced by the build | Every business rule handling money is exercised by a test, and D32 checks the tests would notice it break. Adapters are outside the gate: they are tested where they hold behavior of this service (persistence contract, API contract and errors, security, locks), not to cover configuration, wiring or plain records that the framework already tests. |
| D11 | Health, liveness and readiness probes from day one | An orchestrator needs them to route traffic only to healthy instances and restart stuck ones (NFR4). |
| D12 | Framework-free application layer; dependencies whitelisted by ArchUnit | Use cases are plain Java, testable without a container. Adapters register them as beans. A whitelist (JDK, domain, application) also catches libraries nobody thought to forbid. A use case marks its transaction boundary through the `Transactions` port, and the persistence adapter implements it (D27). |
| D13 | Spring Data JPA, with a native insert-on-conflict to open a wallet | `insert … on conflict (owner_id) do nothing` lets the unique constraint settle concurrent openings in one statement, with no check-then-insert race. `save()` is avoided because it merges entities with assigned ids instead of inserting them. The repository exposes no delete; its only update is the balance, which must run inside a transaction and fails unless exactly one wallet changes. |
| D14 | Wallet and balance are separate resources | The historical balance (FR3) extends `GET /wallets/me/balance` with an instant, so there is a single way to read a balance. |
| D15 | Amounts as decimal strings with a currency code (`"1234.50"`, `"BRL"`) | JSON numbers are parsed as binary floating point by many clients. Same convention as Brazil's Pix and Open Finance APIs. |
| D16 | Flyway owns the schema; Hibernate only validates it | Versioned SQL migrations are reviewable and repeatable (NFR8). `ddl-auto=validate` makes a mapping that drifts from the schema fail at startup. |
| D17 | Business errors as a sealed hierarchy mapped to Problem Details | An exhaustive `switch` maps each error to a status, so adding an error without mapping it does not compile (NFR7). |
| D18 | Configuration through Spring's standard environment variables, no defaults | `SPRING_DATASOURCE_*` and the JWT issuer must be provided; the service fails fast without them. No credential of a deployed environment is committed; `compose.yaml` holds only a throwaway local one, published on the loopback interface. |
| D19 | Integration tests against a real PostgreSQL in Testcontainers, one shared context | Behavior that matters (constraints, concurrency, `timestamptz` precision) is exercised on the real database. Each test uses a fresh owner, which isolates tests without cleanup. |
| D20 | Adapters must not depend on each other, the wiring package included | `adapter.config` wires only through application ports; adapter classes are package-private, so it could not reach them anyway. A bean that needs a concrete adapter is declared in that adapter's own package, as `SecurityConfiguration` is. Exempting the wiring package would weaken the rule for a case that does not exist. |
| D21 | Token audience fixed to `wallet-service`, overridable per environment | Without an audience check, a token issued to any other service of the same provider would be accepted. Spring skips the check when the setting is absent, so a required variable would fail open if forgotten; a fixed value fails closed. It names the service rather than an environment, so D18 does not apply. |
| D22 | One local issuer, the same image in Docker Compose and in tests | Tests validate tokens the issuer signs through the production decoder, so signature, issuer and audience checks are exercised as they run. API tests keep Spring Security's test tokens, which are faster and keep each test focused on the API. The issuer is started by a context initializer, which names it and its key set (D52): the JWT decoder is auto-configured only if they are set before the context refreshes. |
| D23 | Ledger as transactions and entries; the external account has no row | `ledger_transaction` holds type, correlation id and timestamp; `ledger_entry` holds the account (a wallet, or null for the external account), the signed amount and the wallet's resulting balance. Entries share their transaction's timestamp and correlation id instead of copying them. A running balance on the external account would be one row locked by every posting of every user, so the external account keeps none. An identity key gives a wallet's entries a strict order for the historical balance (FR3). |
| D24 | Signed amounts | Positive raises the account's balance, negative lowers it. A deposit is wallet `+a`, external `-a`; a withdrawal is wallet `-a`, external `+a`; a transfer is sender `-a`, recipient `+a`. A transaction balances when its amounts sum to zero, with no debit and credit columns to keep in step. |
| D25 | The database refuses what the code never writes | Triggers reject any update, delete or truncate of ledger rows. A deferred trigger rejects at commit a transaction with fewer than two entries, entries that do not sum to zero, or entries that do not fit its type: a deposit credits one wallet and debits the external account, a withdrawal the reverse, a transfer has two wallet entries and none external. Checks keep wallet balances and resulting balances non-negative, amounts non-zero and balances only on wallet entries, and a unique index allows one entry per wallet per transaction. The domain enforces the same rules first; the database is the last line of defense. |
| D26 | One posting = one transaction under row locks | The use case locks the wallet, or both wallets of a transfer (`select … for no key update`, which blocks other writers of the row but not inserts that reference it), applies the rule, stores every new balance and appends the ledger transaction, in one database transaction. The clock is read under the lock, so a wallet's entries are timestamped in posting order. The lock, the balance update and the append fail outside a transaction (`MANDATORY`), so none can run alone. |
| D27 | `Transactions` port in the application layer | The use case declares where its transaction starts and ends; the persistence adapter implements it with `TransactionTemplate`. Every caller gets exactly one transaction per use case by construction, and unit tests run the use cases with a fake that just calls the work. |
| D28 | Ledger written with plain SQL (`JdbcClient`) | Ledger rows are only inserted and read, so they need no entity lifecycle, and the SQL shows exactly what is written. The sealed entry type maps to rows with an exhaustive `switch`. The wallet stays on Spring Data JPA (D13). |
| D29 | Each wallet lock waits at most two seconds | The lock query carries a lock-timeout hint, which Hibernate applies as `set local lock_timeout` and sets back once the lock is taken: it does not reach the transaction's other statements, nor migrations. A wallet held longer by other operations answers `503` with `Retry-After`, instead of holding a thread and a connection until the client gives up. The transaction is rolled back, so the retry cannot post twice. A transfer takes two locks, each waiting two seconds, within the transaction's three-second budget (D53). |
| D30 | Format checked at the boundary, rules in the domain | Each request type exposes only what the client may set: `amount`, plus `recipientWalletId` for a transfer. The adapter refuses what is not well-formed (`400`): JSON numbers (strict coercion for string fields), anything but a plain decimal string, more than 32 characters, a wallet id that is not a full canonical UUID. The domain refuses what breaks a rule (`422`): not positive, more than 2 decimals, beyond the storable bound (A12), insufficient funds. The positive-amount rule, and for a transfer the same-wallet rule, are also checked before the lock, so a request that can never succeed does not wait for it. |
| D31 | Correlation id taken or generated by a servlet filter before security | The id comes from `X-Correlation-Id` (A13) or is generated, is stored on the ledger transaction and is returned on every response, rejected requests included. A malformed value is refused with a fixed message and never echoed. |
| D32 | Mutation testing on the domain and application layers | Coverage shows a line ran, not that a test would fail if it were wrong. PIT mutates the business rules on every `verify` and fails the build unless every mutant is killed. Adapters are covered by integration tests on the real stack instead. |
| D33 | A transfer is one ledger transaction with an entry on each wallet | The sender's entry is `-a` and the recipient's `+a`, each with its wallet's resulting balance; the external account takes no part. One row in `ledger_transaction` is the atomic unit, so both sides are posted or neither is, and the existing double-entry checks apply as they are. A single `TRANSFER` type serves both sides: the sign of the amount gives the direction. |
| D34 | Transfers lock both wallets in wallet id order | A transfer from A to B and one from B to A, each locking its sender first, would each hold the lock the other waits for. Locking in one global order makes them queue instead. The use case reads the sender's id before its transaction, sorts the two ids and locks them one after the other. Deposits and withdrawals take a single lock, so no cycle can form with them. The order only has to be the same for every transfer, so Java's UUID order serves, though PostgreSQL sorts UUIDs differently. |
| D35 | A lock reads the wallet it protects | Hibernate keeps a wallet read earlier in the transaction in its persistence context, and a locking query hands back that instance as it was read. The repository refreshes the wallet once its row is locked, so a stale balance can never be the base of a posting. A concurrency test found the lost update before the fix. |
| D36 | The recipient is named by wallet id; the counterparty is part of the view | The wallet id is opaque, random and local to this service, unlike the identity provider's subject, which may be guessable or personal data and is valid across the platform (A14). Each side of a transfer sees the other wallet as `counterpartyWalletId`, so the owner's statement shows where money went and where it came from. An unknown recipient is a `422`, keeping `404` for a caller without a wallet. |
| D37 | Idempotency keys in a table of their own, tied to the wallet's ledger entry | A ledger transaction has no single wallet (a transfer touches two), and the key belongs to the wallet that asked. `idempotency_key` holds wallet, key and transaction; its primary key is the wallet and the key, and its foreign key goes through the wallet's own ledger entry, so a key can only name a transaction of its wallet. Rows are append-only, like the ledger, and kept as long as it (A11). The `IdempotencyKeys` port keeps the use case free of storage, with one contract for the fake and the database. |
| D38 | The key is looked up under the wallet's lock; a replay is rebuilt from the ledger | Every posting already locks its wallet, and keys are scoped by wallet, so concurrent retries of one posting queue on that lock (a transfer's on the first of its two, taken in id order): the first posts and records the key in the same transaction, the next ones find it. No in-progress state, no extra lock, no `409` for a request still running. If the first fails, it records nothing and the next one posts. The response is the ledger's view of the transaction, so nothing is stored twice, and comparing a replay's payload with the original (increment 6) needs no copy of the request. The primary key is the last line of defense: a lookup outside the lock fails a concurrency test on it. |
| D39 | A used key replays only the request it was first sent with, compared with the ledger | The retry is compared with the transaction the key names: the same operation, the same amount, as money, and for a transfer the same recipient. That transaction is already read to answer the replay (D38), so no fingerprint of the request is stored and no migration is needed, and `"10.5"` equals `"10.50"` where a hash of the body would not. The correlation id is left out, since each retry may carry its own. The domain answers whether a transaction is what a request would have posted (`isDepositOf`, `isWithdrawalOf`, `isTransferOf` on `WalletTransaction`), keeping signs and types out of the use case: the owner sees a withdrawal or a sent transfer negated, and a transfer must also name the same recipient. A transfer looks its key up once both wallets are locked, before the recipient and balance rules, so a replay succeeds even when the balance no longer covers it; a used key sent to an unknown recipient is a reused key. Checks that touch no wallet (non-positive amount, own wallet) still come first. A mismatch is `422`, as the IETF draft on the header suggests and as every well-formed request that breaks a rule is here; `409` stays for a wallet that already exists. |
| D40 | Offset pagination with totals, read in one statement, ordered by posting | `page` and `size` with totals and a `next` link are what the owner asked for, and the familiar shape of most REST APIs. The count of the wallet's entries and the page are one SQL statement (the page as a lateral subquery left-joined to the count), so they share one snapshot: the totals agree with the page even while postings commit, with no isolation level to set, and a page past the end still answers the totals. The order is the entry's identity key, the strict order of a wallet's postings (D23), not its timestamp, which can tie; the existing `(wallet_id, id)` index serves it, so no migration. `page` and `size` are read as strings and checked in the adapter: Spring's integer conversion would echo the rejected value in its error, which the service never does with untrusted input (D31). Offsets shift when postings arrive while a client pages (see trade-offs). |
| D41 | The balance at an instant is the resulting balance of the wallet's last entry at or before it | Every wallet entry already records the balance it left (D23), and reconciliation tests prove it equals the sum of the entries, so the answer is one row instead of a sum over the history. "Last" is posting order, the entry's identity key, read backwards on the existing `(wallet_id, id)` index with no migration; timestamps can tie, and posting order is the one the stored balances follow. The domain refuses an instant before the wallet or after now (`Wallet.requireBalanceKnownAt`, `422`); the use case reads the instant at its microsecond, as the clock and the database are, and answers zero when the wallet had no entry yet. The read takes no lock, like the current balance (see trade-offs). |
| D42 | The service image is built from source by a multi-stage Dockerfile | Docker is the only prerequisite (NFR10): buildpacks and Jib run Maven on the host, so they need a JDK there. The build stage runs the Maven Wrapper, with the dependencies resolved in a layer of their own so a change to the code reuses them, and skips the tests, which start containers of their own and run in CI's `verify` job. It uses no BuildKit-only syntax, since Compose falls back to the classic builder where buildx is missing. The runtime stage is a JRE on Alpine running Spring Boot's extracted layers, least to most often changed, as a non-root user; the entrypoint is the JVM itself, so `SIGTERM` reaches it. The build context is an allowlist (`mvnw`, the wrapper properties, `pom.xml`, `src/main`), so nothing else on disk can reach the image. |
| D43 | In Compose, the service trusts the issuer by the name clients use and reads its keys over the Compose network | The local issuer names itself after the address it was called at, so a token requested on the host names `http://localhost:9000/local`, an address the service's container cannot reach. The service validates that issuer and the audience as before, and fetches the signing keys from `http://issuer:8080/local/jwks` (`jwk-set-uri`); Spring Boot keeps the issuer and audience validators when the keys come from a set URI. The issuer keeps one identity, as a real provider does, with no network trick and nothing for the client to add; the keys are fetched on the first request, so the service starts without the issuer. Tests name the key set too, since the service no longer discovers it (D52); the collection checks the Compose decoder in CI, a token for another audience or from another issuer included. |
| D44 | A contract written by hand, served by the service | The contract is the API's specification, reviewed as one file, so it is written first and the code follows it. Generated from annotations (springdoc), it would only be as precise as the annotations: the service reads `amount`, `at`, `page`, `size` and the keys as strings and checks them itself, and every error status would need its own annotation on the controller, with no test that they are right. Written by hand, it states the patterns, every error and every header, and adds no runtime dependency. A controller serves it as `application/yaml` (RFC 9512), read once at startup and served whole: a static `.yaml` would be `application/octet-stream`, and a resource body would answer ranges with `206`. It is public, like health: clients and gateways read it before they hold a token, and it grants nothing by itself. |
| D45 | Every API test checks its exchanges against the contract | A test-only MockMvc customizer in the shared integration setup validates every exchange of every API test: the response always (status, headers, body), the request when it succeeded, since error tests send invalid requests on purpose and a success to a request the contract refuses means the two disagree. Response bodies are closed (`additionalProperties: false`), so a field added without the contract fails the build. The check's own tests prove it refuses an undeclared field, status or request. A route test compares the operations the controllers map with the documented ones, both ways, so a route no test calls is caught too. Parameters are declared on operations only: the validator ignores those on a path item, which a guard test found. Security is not checked on test requests, since Spring Security's test tokens set no `Authorization` header; `JwtAuthenticationTest` and the collection send real ones. |
| D46 | A refused token is answered with Problem Details next to the bearer challenge | Clients parse every other error as Problem Details, so a `401` with no body is the one response they would special-case. `BearerTokenProblems`, in the security adapter, delegates to Spring's bearer entry point and access denied handler, which keep the `WWW-Authenticate` challenge of RFC 6750 (`error="invalid_token"` and its description), then writes the body with the fields Spring writes for every other error. The body is the same whatever was wrong with the token, and says nothing about it: the reason stays in the header, where the bearer spec puts it. The body's status is the one the bearer handler chose, since the spec answers a malformed request with `400`. `403` gets the same treatment, though no route asks for more than a valid token yet, so it is pinned by a unit test of the handler. The error dispatch is permitted: a decoder that fails with something other than a token error rethrows its failure to the error page, and refusing that page as anonymous would answer the service's own failure with `401`, telling a client with a valid token that the token was bad (`ErrorPageTest`, on a real server, since MockMvc makes no error dispatch). Keys that cannot be read no longer take that path: they are answered `503` (D52). |
| D47 | One structured access line per request, and the correlation id on every line | Logs are read by machines first: Spring Boot writes Elastic Common Schema natively (`logging.structured.format.console=ecs`), with no encoder dependency, and the same format runs in tests, Compose and production, so what CI sees is what operators get. `AccessLogFilter` is the outermost filter, so it logs every request on the API's port, refusals by security or by the correlation filter included (the management port's are not logged, see trade-offs), with the ECS fields `http.request.method`, `url.path`, `http.response.status_code` and `event.duration` (nanoseconds). It reads the correlation id the correlation filter leaves on the request; a refused id is left out, never written. `CorrelationIdFilter` puts the id in the logging context (MDC) for the rest of the request and takes it off when the request ends, failed or not, so every line logged inside the filter chain carries it. The container logs a failure thrown out of the chain only once that context is gone, so the access line of a `500` is written at `ERROR` with the failure itself (`error.type`, `error.message`, `error.stack_trace`): searching by correlation id finds why the request failed. A failure after the response was sent, such as a client that hung up, keeps the status already sent. Both filters take orders apart from the framework's own first filters (character encoding, observation), so which one wraps the other is defined. Only the path is logged: the query string (`at`, `page`), the body (amounts) and the token (the subject is the user's identity at the provider) stay out. |
| D48 | The actuator on a management port; the probes stay on the application's port | Metrics show traffic, failures and pool usage, which no API client should read, and need no token for a scraper to hold. On a port of its own (`management.server.port=8081`), not published by Compose, they are reached by the platform alone and answer without a token; health is there too. The probes stay where orchestrators already call the service, as `/livez` and `/readyz` (Spring Boot's additional health paths), public as health was; the application's port serves no other actuator path, not even to a valid token. The management port has a security filter chain of its own, matched by the server that received the request (its `WebServerNamespace`), not by path, so it covers every request on the management port and nothing on the API's: a path the management port does not serve is not found there, instead of falling through to the API's chain. It checks no token, since a scraper may send one of its own, such as a service account's, and would be refused. Because that chain is open, the service refuses to start when the management port is the API's or is missing (`SecurityConfiguration.requireManagementPortOfItsOwn`): a configuration slip would otherwise publish the actuator to every client. `-1` is accepted: it turns the HTTP actuator off, and nothing is exposed. |
| D49 | The service's own metrics count operations, never amounts or identities | `wallet.postings` counts postings by `type` and `outcome` (`posted`, or `replayed` from an idempotency key): the use case reports its outcome through the `WalletMetrics` port, after its transaction returned, so a posting rolled back is never counted; Micrometer counts it in `adapter.metrics`. `wallet.refusals` counts the business errors the API answers, missing resources included (`wallet-not-found` on a read is one), by `reason`: the business error's name, read from the sealed hierarchy, so a new error gets a series with nothing to add, and `wallet-busy` for a lock that timed out. Every series is registered at zero at startup, so a rate exists before the first event. Amounts and wallet ids are left out: money is the ledger's to report, and per-user tags would grow without bound. Request, JVM and connection pool metrics are Spring Boot's own. |
| D50 | The database in the readiness group; `503` when it is unavailable | Without its database the service can answer no request, so readiness includes Spring Boot's own `db` indicator (`management.endpoint.health.group.readiness.include=readinessState,db`): the orchestrator routes traffic to instances that can serve it. Liveness leaves it out, since restarting instances cannot bring a database back. The indicator takes a connection from the pool requests use, so it proves what they need. A query that cannot get or keep a connection raises `DataAccessResourceFailureException`, and a use case that cannot start its transaction `CannotCreateTransactionException`, as probes on the stack found; `WalletProblemHandler` answers both with `503`, `Retry-After: 1` and a fixed detail that names neither the pool nor the driver. Other data errors stay `500`: they are defects, not outages. The pool waits two seconds for a connection instead of Hikari's thirty, like the lock wait (D29), and validates one in a second at most (Hikari does not bound validation by the wait), so the answer comes in about two seconds. The failure is logged once, at `ERROR` with its cause, while the request's correlation id is still in the logging context: answered by the handler, it no longer reaches the access line (D47). It is not a refusal, so `wallet.refusals` does not count it; request metrics count the `503`, and Hikari's own metrics the timeouts. The test stops a database of its own in a context of its own (`DatabaseOutageTest`), since stopping the shared one would break every other integration test. |
| D51 | A posting that loses its connection fails as a database failure | PostgreSQL ends every connection when it restarts or fails over (`57P01`), so a posting can lose its connection while it runs. Two rules in the persistence adapter keep that failure a `503` (D50). Hibernate's PostgreSQL dialect reads a lost socket (class 08) as a lost connection, but the states the server ends connections with (`57P01`, `57P02`, `57P03`) as generic errors, which Spring answers as a failure of the service; `ShutdownAwarePostgreSQLDialect` (`spring.jpa.database-platform`) reads them as lost connections too, and every other failure as PostgreSQL's dialect does. Spring's own translation is left as it ships: handing Hibernate's failures to a Spring translator, even one limited to these states, also replaces the one Spring applies to a failed commit, and the full build caught the deferred ledger checks' refusals turning into generic errors. And when the work fails and the rollback then fails on the dead connection, `SpringTransactions` throws the work's failure, with the rollback's suppressed: `TransactionTemplate` would throw the rollback's, a `Connection is closed` with no SQLState that says nothing of why, while a connection that is gone committed nothing. Opening a wallet declares its transaction through the `Transactions` port too, like every posting (D27), so the rule reaches it. CI found the case, and `ConnectionLossApiTest` pins it: it ends the connection of a deposit waiting for its wallet's lock, then the same key posts once, and of a wallet opening waiting for another one of the same owner. |
| D52 | A token that cannot be checked is `503`; the keys are read from a named key set, within two seconds | When the issuer's keys cannot be read, the token was neither accepted nor refused: like an unavailable database (D50), it is a dependency failure, answered `503` with `Retry-After: 1`, no bearer challenge and a fixed detail, and logged once at `ERROR` with its cause and the correlation id. `JwtAuthenticationProvider` raises it as an `AuthenticationServiceException` over a `JwtException`; `BearerTokenProblems` answers it as the bearer filter's failure handler, set through an object post-processor since the configurer has no setter, and rethrows any other service failure to the error page, as Spring's default handler does, since the filter also catches what is thrown further down the chain. Spring Security reads a key set for up to 30 seconds to connect and 30 to read, and Nimbus makes concurrent requests wait up to 15 seconds for one request's refresh; discovery is worse, since the decoder it builds sits behind a lock that makes each request retry in turn until the first success. So the service does not discover the key set: it requires the issuer and its key set (`issuer-uri`, `jwk-set-uri`) and refuses to start without either, which also keeps a key set alone from accepting tokens of any issuer it signs for. `IssuerKeys`, a `JwkSetUriJwtDecoderBuilderCustomizer`, keeps the decoder Spring Boot builds, with its issuer, audience, expiry and type validators, and swaps only its key selector for one over a Nimbus key source with Spring Security's caching settings, a read with one deadline of two seconds (`DeadlineRetriever`: name lookup, connect and reads together, interrupted at the deadline) and a refresh wait of two seconds. A request answers in two seconds, four when it reads after waiting for another request's read, as `IssuerTimeoutTest` measures with eight concurrent requests against an issuer that never answers. Readiness does not follow the issuer: keys already read keep checking tokens, and the identity provider is shared by the whole platform (see trade-offs). A token sent to a public path is checked too, so it gets the same `503` there. It is not a refusal, so `wallet.refusals` does not count it. |
| D53 | Every posting and wallet opening runs within a three-second budget the database keeps | The wallet lock's timeout covers that lock alone: a posting also waits on other locks, such as a migration's table lock, and a wallet opening waits, with no lock query at all, behind another opening of the same owner; both waited forever. `SpringTransactions` sets PostgreSQL's `transaction_timeout` (`set local`, 3,000 ms) as the first statement of every use-case transaction, so the server ends it when the budget runs out, whether a statement runs, waits for a lock, or the service is between statements; a transfer's two lock waits, four seconds before, fit in it. A probe on PostgreSQL 18.6 showed the clock starts at the `set` and the setting ends with the transaction, so migrations, readiness and reads are untouched. The server ends the connection with the transaction (`FATAL`, `25P04`); the pool marks it broken and opens another. Neither Hibernate nor Spring knows the code, so `SpringTransactions` finds it anywhere in the failure and throws Spring's `TransactionTimedOutException`, which `WalletProblemHandler` answers `503` with `Retry-After: 1` and a fixed detail, logged once at `ERROR` with the correlation id and not counted as a refusal, like an unavailable database (D50). Spring's own transaction timeout was built first and dropped after the code review: it limits each statement through JDBC's whole seconds, and Hibernate rounds the time left to the nearest second, so a statement started with less than half a second left had no limit at all (`SpringTransactionsTest.cutsAStatementStartedNearTheEndOfTheBudget`). A `statement_timeout` bounds each statement, not their sum. A `503` is retried with the same `Idempotency-Key`, which replays a posting the database had already committed. |
| D54 | Graceful shutdown bounded at ten seconds, below the platform's kill | Spring Boot 4.1.2 shuts down gracefully by default. On `SIGTERM` (D42), Tomcat closes its server socket, so new connections are refused at once; it closes a kept-alive connection without reading another request on it, so a posting sent there is not posted; and it waits for the requests in flight, which still reach the database, since the pool closes only after the drain. Spring's default bound of 30 seconds was never the one that applied: Docker kills a container ten seconds after `SIGTERM`, and Kubernetes after 30. `spring.lifecycle.timeout-per-shutdown-phase=10s` covers the longest request the service bounds, about nine seconds (a key read of four at most, D52; a connection wait of two, D50; the posting budget of three, D53). A request that outlasts it is cut: the API's server then stops in about 12.3 seconds, two of them Tomcat waiting for the servlet to be released, and the management server drains after it in a phase of its own, up to about three seconds more for a health check on an unavailable database. Compose's `stop_grace_period: 20s` covers both. HikariCP aborts the connections still in use when it closes, so the pool adds no wait. A posting cut by the shutdown commits or rolls back whole, and is retried with its `Idempotency-Key`. `GracefulShutdownTest` starts a service of its own for each test, since each test stops it, and sends requests over plain sockets, so a test chooses the connection each one travels on. |

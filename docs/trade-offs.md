# Trade-offs

Compromises made consciously, why, and what a production rollout would add. This document grows with each increment.

Each compromise has a kind: a **design choice** would stay the same with more time, because it is the right call for this service; a **time constraint** is deferred and has a planned production path.

## Trade-offs

| Area | Kind | Compromise | Why | Production path |
|---|---|---|---|---|
| Database availability | Design choice | A single PostgreSQL instance | Replication and failover are infrastructure concerns, outside the service code | Managed PostgreSQL with synchronous replicas and automatic failover |
| Transport security | Design choice | TLS is not terminated by the service | Keeps the service runnable out of the box, without self-signed certificates | TLS at the gateway or ingress, mTLS between services |
| Token issuance | Design choice | mock-oauth2-server issues tokens for local runs and tests, to anyone who asks | Identity management belongs to a dedicated provider | Point the resource server to the real identity provider |
| Module boundaries | Design choice | Layering enforced by tests, not by the compiler | A single module keeps the build simple | Split into Maven modules if the codebase grows |
| Hot wallets | Design choice | Pessimistic locks serialize operations on the same wallet | Correctness first; contention on a single wallet is rare for end users. A wallet that receives many transfers, such as a merchant's, is locked by each of them | Sharded balances or asynchronous posting for high-volume accounts |
| Refused token detail | Design choice | A refused token's Problem Details body says only that a valid bearer token is required; why it was refused (expired, wrong audience, bad signature) is in the `WWW-Authenticate` header alone | The bearer token spec puts the reason in the challenge, which clients and libraries already read; one fixed body never echoes anything taken from the token | None needed; log the reason server-side if support ever needs it per request |
| Forbidden responses | Design choice | The `403` Problem Details answer is pinned by a unit test of its handler, not end to end, and is not in the contract; a change that dropped the handler from the security configuration would pass every test | No route asks for more than a valid token, so nothing reaches `403` today; a test-only route asking for a scope would test the framework's wiring | Document `403` in the contract and test it end to end with the first route that asks for a scope or role |
| Issuer outage | Time constraint | When the issuer's keys cannot be read, a request with a token answers `500` with Spring Boot's generic error body, not Problem Details, and is not in the contract | The failure now reaches the error page instead of being taken for a bad token (D46); giving it its own status belongs with the other dependency failures | `503` with `Retry-After` for an issuer that cannot be reached, next to the database's (increment 15) |
| Problem Details writers | Design choice | Three places write Problem Details: Spring MVC, `BearerTokenProblems` and `CorrelationIdFilter`'s fixed refusal, which still sends `"type": "about:blank"` and no `instance`, unlike the other two | Security and the correlation filter answer before MVC runs, so they cannot use its converters without wiring MVC into the filter chain; the shapes differ only in optional fields RFC 9457 lets a client ignore | One writer shared by the filters, in the final review (increment 18) |
| Protected resource metadata | Time constraint | Spring Security 7 serves `GET /.well-known/oauth-protected-resource` (RFC 9728) without a token and points the `WWW-Authenticate` challenge at it; the document is not in the contract, names no authorization server and states `tls_client_certificate_bound_access_tokens: true`, which this service does not enforce | It is the framework's default, found while building this increment, and grants nothing; changing it is outside this increment's behavior | Decide in the final review (increment 18): turn it off, or configure it with the real issuer and document it in the contract and NFR9 |
| Log format | Design choice | Logs are JSON everywhere, a developer's console and test output included | One format means what tests and CI print is what production ships; `jq` reads it on a laptop | Keep JSON in every environment; a human-readable format through `logging.structured.format.console` only if a team asks for it |
| Access log content | Design choice | The access line names the path, which holds transaction ids, but not the user, the query string or the body | Ids are opaque and grant nothing without the owner's token; the token subject is the user's identity at the provider, personal data the log does not need, and the correlation id already ties the line to the ledger | Add the wallet id, not the subject, if support needs to find a user's requests |
| Raw path in the access log | Design choice | The access line writes the path as the client sent it, percent-encoding and `;` parameters included, up to the container's header limit | Spring Security's firewall refuses `;` and encoded slashes right after, and the routes carry no secret in the path; a normalized path would hide what was actually sent | Log the matched route pattern next to the path if paths ever carry personal data |
| Failure logged twice | Design choice | A `500` is logged twice: on the access line, with its correlation id, and by the container, without it | The container's line is written after the request's context is gone, and silencing it would hide failures thrown outside the filters | Turn the container's logger for the dispatcher servlet down once every failure is known to reach the access log |
| Probe requests in the access log | Design choice | Probe requests (`/livez`, `/readyz`) are logged like any other request; Compose probes every two seconds | Leaving them out takes a list of paths to keep in step with the probes; a log pipeline drops them by path at no cost to the service | Drop or sample probe lines in the log pipeline |
| Business events | Time constraint | Postings are not logged as events of their own; the access line and the ledger, which keeps every transaction with its correlation id, are the trail | The ledger is the audit record (NFR1); a second record in the logs would need its own rules for amounts and identities | Publish posting events to an event stream if downstream systems need them |
| Management port without a token | Design choice | Anyone who reaches port 8081 reads the metrics and health without a token | Scrapers rarely hold tokens, and the port is the platform's: Compose does not publish it, and a deployment exposes it to the cluster network only. The metrics hold counts, never amounts or ids (D49) | A network policy that admits only the scraper to the management port |
| Metrics without amounts | Design choice | Metrics count postings but not the money they move | Amounts are the ledger's, audited and reconciled; a sum in a metrics backend would be a second, unreconciled record of balances | Money flows reported from the ledger, by a reporting job or a read replica |
| Wallet ids | Design choice | Random UUIDs (v4) as primary keys | The JDK generates them with no extra code | Time-ordered UUIDs (v7) for better index locality at high insert rates |
| Local credentials | Design choice | `compose.yaml` holds a fixed PostgreSQL password | It protects a throwaway database bound to the developer's machine | Credentials from a secret manager, never in the repository |
| Token expiry | Time constraint | Expiry is validated by Spring Security's defaults, without a test of our own | We do not configure it, and an expired token needs extra issuer setup | A test with an expired token if the clock skew is ever tuned |
| Issuer identity in Compose | Design choice | The service in Compose accepts only tokens that name `http://localhost:9000/local`, so a client must request them at that address: one requested at `127.0.0.1:9000`, or by a container on the Compose network at `issuer:8080`, names another issuer and gets `401` | The local issuer names itself after the address it was called at and cannot be given a fixed name; the address clients on the host use is the one trusted, and the service reads the keys over the Compose network (D43) | A real identity provider has one issuer URL, reachable by clients and services alike; the service then uses issuer discovery alone, as it does in tests |
| Stored balance | Design choice | The wallet row keeps the current balance next to the ledger, updated in the same transaction as every entry | Reading a balance stays one row lookup instead of a sum over the ledger; the lock that serializes postings is on that same row | The ledger is the source of truth: a test reconciles the stored balance with the entries; production adds a scheduled reconciliation job that alerts on any drift |
| External account | Design choice | The external account keeps no running balance; its entries have no resulting balance | A running balance would be one row locked by every deposit and withdrawal of every user | Its balance is the sum of its entries; settlement with payment providers would reconcile against it |
| Database outage | Time constraint | Readiness does not check the database, a database that is down answers `500` with a generic body, and statements have no timeout | Only the lock wait introduced in this increment is bounded now | Database in the readiness group and `503` on connection failures (increment 15), a statement timeout (increment 16) |
| Busy wallet and the connection pool | Time constraint | Requests waiting for one busy wallet's lock each hold a pooled connection for up to two seconds, so a burst on a single wallet can delay requests for other wallets | The lock wait is bounded and the case needs one user flooding their own wallet | Size the pool for the expected concurrency, and limit concurrent postings per wallet at the gateway or in the service |
| Ledger balance check | Design choice | The deferred check runs once per inserted row, so a two-entry posting sums its entries three times at commit | Each run is an indexed lookup of a few rows; a per-statement check needs triggers PostgreSQL does not allow to be deferred | A single check per transaction id if postings ever carry many entries |
| Request body size | Design choice | The service sets no limit on request body size | The only body is one short field; size limits belong to the gateway, in front of every service | Body size limit at the gateway or ingress |
| Correlation id trust | Design choice | The service accepts the caller's `X-Correlation-Id` after checking only its format; it is neither unique nor authenticated, so two requests, even from different users, can share one | It only groups entries for tracing: it is never used for authorization, lookups or deduplication, and each transaction keeps its own generated id. A repeated id is even useful, since it shows the same request was posted twice | The gateway generates or overwrites the header and the service trusts it only from the internal network; searches by correlation id filter by wallet too |
| Adapter coverage | Design choice | The coverage gate covers the domain and application layers only | A test written only to cover configuration, wiring or plain records re-tests the framework and adds upkeep without catching our defects | Adapter behavior stays covered by integration tests: persistence contracts, API, security, locks |
| Concurrency test timing | Design choice | `LedgerConcurrencyTest` expects all 32 postings on one wallet to clear the two-second lock wait | Each posting holds the lock for a few milliseconds, so 32 of them clear it with a wide margin; a runner slow enough to miss it fails the test rather than hiding a defect | Raise the lock wait for tests only if CI ever shows it |
| Recipient addressing | Design choice | A transfer names the recipient by wallet id, which cannot be rotated and is shared outside the service | The id is opaque, random and local to this service, unlike the identity provider's subject; aliases belong to user management, which is out of scope (A14) | Revocable aliases (phone, e-mail, random key) resolved to wallet ids by a directory service |
| Recipient existence | Design choice | Any authenticated caller learns whether a wallet id exists, at no cost, since a refused transfer moves nothing; the refusal for a recipient near the storable bound also tells the sender that much about its balance | Wallet ids are random UUIDs (v4) and cannot be enumerated; the bound is about 10^17 BRL | Limit transfer attempts per caller at the gateway and alert on repeated unknown-recipient refusals |
| Transfer lock wait | Design choice | A transfer takes two locks, each waiting up to two seconds, so it can wait four seconds; while it waits for the second wallet it holds the first, so that wallet's other operations wait too | Ordered locking must hold the first lock to take the second; the wait stays bounded and the client gets `503` with a safe retry | A time budget for the whole transaction (statement timeout, planned in increment 16) |
| Lock refresh | Design choice | Every lock reads its wallet once more, after the row is locked | One primary-key read per posting buys a lock that can never hand back a stale balance, whatever the transaction read before (D35) | If profiles ever show it, read only ids before locking and drop the refresh where nothing can be stale |
| Replay under the lock | Design choice | A retry waits for the wallet's lock like any posting, so on a busy wallet it can get `503` even though its posting was already made; a transfer's retry waits for both wallets' locks, so a busy recipient delays it too | Looking the key up under the lock is what makes concurrent retries post once with no in-progress state (D38); the `503` moves nothing and the next retry gets the original | Look the key up before the lock as well, as a fast path for replays, keeping the check under the lock |
| Idempotency key format | Design choice | The key is a bare token; the IETF draft on the header (an Internet-Draft, not an RFC) defines it as a quoted structured-field string, which the service refuses with `400`, and suggests `409` for a request still running, where the service waits and replays | Bare keys are what payment APIs widely use, and one format with the correlation id keeps validation simple (A17); waiting gives the client its answer instead of a conflict to retry | Accept the quoted form too if the draft becomes an RFC |
| Idempotency key retention | Design choice | Keys are never deleted, so the table grows with the ledger | A retry may come at any time, and a key that expired could post twice (A11); a key row is a few dozen bytes next to the entries it names | Archive keys together with the ledger transactions they name, once a retention policy exists |
| History paging | Design choice | Pages are read by offset, so a posting that arrives while a client pages shifts the history: the next page repeats the last transaction already seen (a transaction can be skipped only if the ledger shrank, which it never does). A deep page makes the database walk past every skipped entry | Page numbers with totals are what the owner asked for and what clients browse a statement with; the wallet's index keeps the walk to its own entries, and the repeat is visible by transaction id | A cursor on the entry order (`where id < :last`, same index) for clients that sync or export the whole history, next to the numbered pages |
| History totals | Design choice | Every page counts all of the wallet's entries, so the cost of a page grows with the history | The count runs in the same statement as the page, on the wallet's index, so totals always agree with the page (D40) | Keep a transaction counter on the wallet row, updated with the balance, or drop the totals for cursor clients |
| Recent instants | Design choice | The balance at an instant inside a posting that is still committing leaves that posting out, and includes it once it commits; for that moment the current balance and the balance at now can disagree the same way | A posting is stamped under the wallet's lock and becomes visible at commit, a few milliseconds later; reading under the lock would make every balance read wait for postings, and risk a `503`, to settle an instant that old enough reads never meet | Answer only instants older than a transaction's time budget (statement timeout, increment 16), or read under a share lock of the wallet |
| Clock order | Design choice | Postings are stamped by each instance's wall clock, so a clock that steps back, or two instances whose clocks differ, can stamp a later posting earlier. The balance at an instant follows posting order, so it can then include a posting stamped after that instant, and an instant the service has just returned can read as the future | Clocks are kept in sync by NTP and steps are rare and small; posting order is the one the stored balances follow (D23, D41) | Stamp postings with the database clock, or never earlier than the wallet's last posting, under its lock |
| Historical balance cost | Design choice | An instant far in the past walks the wallet's entries back from the newest, one transaction lookup each, until one is not after it | One statement on the wallet's existing index and no migration; a wallet's history is short next to the lookup's cost | Copy `created_at` onto `ledger_entry` and index `(wallet_id, created_at)`, or keep periodic balance snapshots |
| Relative links | Design choice | `next`, like `Location`, is a path that assumes the service is served at the root | The service runs at the root, and a gateway that adds a prefix rewrites paths for every service alike | Build links from the forwarded request (`X-Forwarded-Prefix`) if the service is ever exposed under a prefix |
| Image build and tests | Design choice | The image build compiles and packages the service without running its tests | The tests start PostgreSQL and the issuer in containers of their own, which a build inside Docker cannot do without access to the Docker daemon; CI's `verify` job runs them on the same commit, and the `compose` job runs the collection against the built image | Build the image once in the pipeline after `verify` passes, push it to a registry, and deploy that same image |
| CI image build | Design choice | CI's `compose` job builds the image from scratch on every run, downloading the dependencies again: about a minute and a half on GitHub's runners, five on a laptop VM | The job proves the README path as a reviewer meets it, with no cache to hide a broken build; it runs next to `verify`, not after it | Cache the image layers between runs (buildx with the GitHub Actions cache), or build once and reuse the image across jobs |
| API contract upkeep | Design choice | The OpenAPI contract is written by hand, so every new endpoint, field, status or header means editing it as well as the code | Written first, it states what the code checks by hand and every error, which annotations would not (D44); a contract left behind fails the build, through the route test and the check on every API test's exchanges (D45) | Publish the contract to an API registry, and generate client SDKs and consumer contract tests from it |
| Contract check reach | Design choice | The check sees what the tests send and receive: requests only when they succeeded and without their token, responses only of exchanges some test makes. A contract more permissive than the service, one that allows a request the service refuses with `400`, goes unseen | Error tests send invalid requests on purpose; the route test covers operations no test calls, `JwtAuthenticationTest` and the collection send real tokens | Generate negative tests from the contract (property-based fuzzing such as Schemathesis) and run them against the Compose stack in CI |
| Instants the contract asks for | Design choice | The contract asks for `at` as an RFC 3339 `date-time`; the service also accepts the ISO-8601 forms RFC 3339 does not, such as an instant without seconds (`2026-11-09T10:00Z`) | A client that follows the contract is always understood; tightening the service would change the behavior A21 defines, and a regex copying the parser would drift from it unseen | Refuse what RFC 3339 does not allow in a later version of the API, announced through the contract |
| Transaction id format | Design choice | `GET /wallets/me/transactions/{id}` accepts the short forms Java reads as a UUID (`1-1-1-1-1`) and answers `404`, where the contract asks for a full UUID and promises `400` for anything else | `404` is a status the contract documents, and no transaction id takes a short form; wallet ids in a request body are already checked in full (D30) | The same canonical check on the path id, in the final review (increment 18) |
| Public contract | Design choice | `GET /openapi.yaml` needs no token, so anyone who reaches the service reads its routes, fields and errors | The repository is public, and the contract grants nothing: every wallet operation still needs a valid JWT. A token sent to a public path is still validated, and a bad one gets `401` | Serve the contract through the gateway or a developer portal, and close it at the gateway if a policy asks for it |
| Statuses not listed per operation | Design choice | The contract does not list per operation `405`, `406` or the `500` a database outage answers today | `405` and `406` come from HTTP itself, for requests outside the contract; listing them on every operation adds noise. The contract says so once | The `500` becomes a documented `503` with the database in the readiness group (increment 15) |
| OpenAPI version | Design choice | The contract is OpenAPI 3.1, which tools that know only 3.0 cannot read | 3.1 is JSON Schema 2020-12 (`const`, typed `additionalProperties`), the current version, read by current validators, linters and generators | Publish a 3.0 copy converted from it if a consumer's tooling requires one |
